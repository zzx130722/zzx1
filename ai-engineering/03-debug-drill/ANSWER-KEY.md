# 答案册：5 个 bug 的根因、修法，和「怎么问 AI 才问得到根因」

> 先跑 `drill.py`（不带 `--answers`），把 5 句根因写在纸上，再往下看。

---

## 第 1 关：`cart=[]` 是可变默认参数

```python
def add_to_cart(item, cart=[]):   # ← 这个 [] 只创建一次
```

**根因**：默认参数在**函数定义时**求值一次，之后所有调用共用同一个列表对象。
不是"每次调用重新创建一个空列表"——这是 Python 里最反直觉的一条。

**最小复现**：
```python
add_to_cart("apple")    # ['apple']
add_to_cart("banana")   # ['apple', 'banana']  ← 期望 ['banana']
```

**修法**：
```python
def add_to_cart(item: str, cart: list[str] | None = None) -> list[str]:
    if cart is None:
        cart = []
    cart.append(item)
    return cart
```

**为什么难发现**：第一次调用永远是对的。单测如果只写一个用例，必然绿。

## 第 2 关：`get_items()` 把内部列表的引用交出去了

```python
def get_items(self):
    return self._items          # 不是副本，是同一份数据
```

**根因**：Python 的赋值和传参都不是复制。调用方拿到的 `borrowed` 就是 `self._items` 本身，
`borrowed.append(...)` 等价于直接改库存。

**最小复现**：
```python
inv = Inventory(["pen", "book"])
inv.get_items().append("eraser")     # 看起来只是改了个临时变量
inv.count()                          # 3 ← 期望 2
```

**修法**（二选一，看语义）：
```python
return list(self._items)             # 给副本，调用方随便改
return tuple(self._items)            # 给不可变视图，想改就直接报错
```

第二种更好：**它把"不许改"这件事写进了类型里**，而不是靠注释提醒。

**为什么难发现**：没有任何报错。数据是被"合法地"改坏的，测试不覆盖这个路径就永远看不到。

## 第 3 关：`//` 是整除，不是"精确除法"

```python
return total // people        # 137.5 // 3 → 45.0
```

**根因**：`//` 是**向下取整除法**，结果是 `float` 但已经把小数部分抹掉了
（`137.5 // 3 = 45.0`，不是 `45.8333`）。钱按这种方式分，每份都少了零头，加起来就对不上账。

**最小复现**：`137.5 / 3 = 45.8333...`，`137.5 // 3 = 45.0`，三人合计 135.0，凭空少 2.5 元。

**修法**：金额用 `Decimal`，并且**明确"余下的几分钱给谁"**：
```python
from decimal import Decimal, ROUND_DOWN

def split_bill(total: Decimal, people: int) -> list[Decimal]:
    if people <= 0:
        raise ValueError("people must be positive")
    each = (total / people).quantize(Decimal("0.01"), rounding=ROUND_DOWN)
    shares = [each] * people
    shares[-1] += total - each * people    # 零头全给最后一个人，保证加起来等于总额
    return shares
```
注意返回值从「一个数」变成了「一个列表」—— 因为"每人一样多"这个前提在分钱时**根本不成立**。
这个改动会波及调用方，所以它属于**接口变更**，要和重构分开做（不能混在同一次提交里）。

**为什么难发现**：整数金额（比如 120 元 3 人）算出来是 40，完全正确。

## 第 4 关：`try` 包住了整个 `for`，第 2 行一错，后面全没读

```python
try:
    with open(path) as handle:
        for line in handle:              # ← 循环在 try 里面
            ...
            prices[name] = float(raw)    # banana 这行在这里抛 ValueError
except Exception:
    pass                                 # ← 异常被吃掉，函数安静返回
```

**根因**：两个错误叠在一起。
① `try` 的范围是**整个循环**，第 2 行抛错 → 循环中断 → 第 3、4 行根本没被读到；
② `except: pass` 把这个事实藏了起来，调用方看到的是"只读到 1 条"，而不是"出错了"。

正确的写法是 `try` 只包**一行**：
```python
for line in handle:
    try:
        name, raw = line.strip().split(",")
        prices[name] = float(raw)
    except ValueError:
        warnings.append(f"skip bad line: {line.strip()!r}")
        continue                          # ← 只跳过这一行，继续读下一行
```

**为什么难发现**：`except: pass` 让"读到 1 条"看起来就像"文件里只有 1 条"。
**数据静默缺失比程序崩溃危险一百倍**——崩溃至少会有人去看。

> 顺带一个能观察到的细节：如果你自己用记事本另存这个 csv，key 可能变成 `'\ufeffapple'`。
> 那是 UTF-8 BOM 混进了第一个字段名。读文件时用 `encoding="utf-8-sig"` 就能自动去掉。
> 这个坑单独说不明显，但在 Windows 上和 Excel 打交道的项目里天天遇到。

## 第 5 关：`sales` 是字符串，`sorted` 按字典序比

```python
sorted(rows, key=lambda row: row["sales"], reverse=True)
# "9.5" > "8.0" > "100.0" > "10.0"   ← 字典序，不是数值序
```

**根因**：字典序是**逐字符**比较的。第一个字符 `'9' > '1'`，所以 `"9.5"` 排在 `"100.0"` 前面，
后面的字符根本没机会参与比较。

**最小复现**：
```
A: 9.5   B: 10.0   C: 8.0   D: 100.0
结果：['A', 'C', 'D']       期望：['D', 'B', 'A']
```

**修法**：
```python
return sorted(rows, key=lambda row: float(row["sales"]), reverse=True)[:3]
```
更彻底的做法是**在数据进入系统时就转成 `Decimal`**，而不是在每个用到的地方都 `float()` 一次。
类型不对的数据，越早转换越好——放在 `sorted` 里转换，意味着其他用到 `sales` 的地方还留着同一个坑。

**为什么难发现**：所有"位数相同"的数字，字典序和数值序恰好一致（`"8.0"` vs `"9.5"` 就是对的）。
只有位数不同才暴露 —— 而测试数据往往是随手写的个位数。

## 这 5 个 bug 为什么能活下来？

它们有一个共同点：**在"正常输入 + 只跑一次"的情况下全部正确**。

| bug | 什么条件下才暴露 |
|---|---|
| 1 可变默认参数 | 同一个函数被调用**第二次** |
| 2 返回内部引用 | 调用方**修改**了返回值 |
| 3 整除丢零头 | 金额**不能被人数整除** |
| 4 try 范围过大 | 文件中间有**一行坏数据** |
| 5 字符串排序 | 数字**位数不同** |

所以测这些 bug 不需要更多用例，只需要**换一种调用方式**：
调两次、改一下返回值、用除不尽的数、在中间插一行坏的、用 9 和 100 一起排。

## 怎么问 AI，才问得到根因

### 三种坏问法

| 问法 | 你实际会得到什么 |
|---|---|
| "这段代码有 bug 吗？" | 5 条命名建议 + "建议加类型注解" + 1 条真问题混在里面 |
| "帮我修一下" | 一段能跑的代码。你学不到任何东西，而且它可能顺手改掉别的地方 |
| "为什么输出不对？" | 它只能猜。因为你没说输入是什么、期望是什么、实际是什么 |

### 好问法：把自己的假设摆上桌，让它否证

```text
我怀疑第 4 关的根因是「try 包住了整个 for 循环」，
证据是：把 prices.csv 里 banana 那行删掉之后，4 条里能读到 3 条。

请只回答两点：
1. 这个判断对不对？如果不对，指出我漏了什么。
2. 如果对，为什么把 try 挪进循环里就能修好？用一行话说清机制。

不要给修复代码。
```

这个问法有三个好处：**你有假设**（不是空手要答案）、**你有证据**（删掉坏行后现象消失，
这是定位的硬依据）、**你限制了输出**（不要代码，只要机制）。

第 2 问最关键：**"为什么挪进去就好了"** —— 这才是根因。
只知道"挪进去能修好"是照抄，知道"因为 try 的范围决定了谁被跳过"才是理解。

### 一个通用模板

```text
【输入】具体数据，别写"一些数据"
【期望】具体值，别写"正确的值"
【实际】具体值，贴原始输出
【我的假设】我认为是 X，因为 Y
【要你做什么】只判断假设对不对 / 只解释机制 / 只给最小复现
```

前四条凑齐，AI 的定位准确率会从"猜"变成"查"。
第五条决定你拿到的是知识还是代码。

## 自测：不看上面，能答出几个？

1. 为什么 `def f(x=[])` 里的 `[]` 只创建一次，而 `def f(x=None)` 里每次都要新建？
2. 第 2 关除了 `return list(...)`，还有什么修法能让"改返回值"直接报错？
3. 第 3 关如果坚持 `//`，总额会少多少？能不能用"最后一个补差"绕过去？
4. 第 4 关如果把 `except: pass` 改成 `except: raise`，现象会变成什么？
5. 第 5 关的 bug，用 `float()` 修好之后，还有没有别的地方会踩同一个坑？

第 4 题的答案值得想清楚：改成 `raise` 之后程序会崩在第 2 行 ——
**从"静默少数据"变成"立刻崩"，这是改善**，但它不是最好的方案（最好的是跳过坏行 + 警告）。
