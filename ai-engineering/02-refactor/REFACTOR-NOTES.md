## 一、重构的顺序，比重构的技巧重要

绝大多数人重构失败，不是因为不会拆函数，而是**顺序错了**：先动手改结构，改到一半发现行为变了，
又回头找"到底哪一步改坏的"，最后放弃。

正确顺序是四步，**前两步一行业务代码都不改**：

| 步 | 做什么 | 这一阶段不许做什么 |
|---|---|---|
| 1 | **立安全网**：先写 `check_equivalence.py`，跑通"新旧输出一致" | 不许改逻辑 |
| 2 | **搬家**：把代码切成几个模块，逻辑照抄 | 不许改任何一行计算逻辑 |
| 3 | **补类型**：加注解、换 `Decimal`、加自定义异常 | 不许改输出格式 |
| 4 | **改行为**：修 bug、加警告 | 每改一条，立刻跑第 1 步的脚本 |

第 1 步的"安全网"就是这次交付里的 `check_equivalence.py`。
它比任何"重构后看起来没问题"都可靠——眼睛看 100 行代码是看不出 `amt` 那个 bug 的。

## 二、改了什么（7 项）

| # | 原版 | 重构版 | 为什么 |
|---|---|---|---|
| 1 | 0 个函数，60 行平铺 | `models / errors / loader / report / cli` 五层 | 每层只干一件事：**定义数据 / 定义错误 / 读文件 / 算 / 交互** |
| 2 | 无类型注解 | 全部函数带参数与返回类型 | 改错参数名、传错类型，编辑器当场报红，不用等运行 |
| 3 | `float` 算钱 | `Decimal` + `quantize(0.01)` | 钱不能有二进制误差；`0.1 + 0.2 != 0.3` 在账上是要出事的 |
| 4 | `except: pass` | `RowParseError` / `CsvFormatError`，带行号 | 裸 `except` 连 `Ctrl+C` 都吞。而且吞了之后**没人知道数据少了** |
| 5 | 硬编码路径 + 手写 `open/close` | `argparse` + `with open(...)` | 路径可配；异常时文件句柄也会关 |
| 6 | 手写冒泡排序，只跑一趟 | `sorted(key=(-金额, 区域))` | 见下面 bug 2 |
| 7 | 没有任何去重 | `dedupe_by_order_id` + 警告 | 见下面 bug 3 |

拆分之后最直接的好处：`report.py` 里的 `summarize()` 和 `render()` **不碰文件、不打印**，
所以 `04-pytest` 里可以一行 `summarize([...])` 直接测它。原版那段代码离不开 CSV 文件，根本没法测。

## 三、三个 bug，和它们的证据

这三个 bug 都在**脏数据**上才会发作。干净数据上两版输出完全一样——这就是为什么它们能活很久。

### bug 1：`amt` 定义在循环外 → 解析失败时沿用**上一行的金额**

```python
amt = 0.0                      # ← 在 for 外面
for i in range(1, len(rows)):
    row = rows[i]
    try:
        amt = float(row[3])    # ← 失败时 amt 保持上一轮的值
    except:
        pass
    a[row[1]] = a[row[1]] + amt
```

Python 的循环变量不会每轮重置。`float("1,234.50")` 抛异常 → `amt` 仍是上一行的 `45.50`
→ 这行的销售额被记成 45.50，而且**记在了当前区域头上**。

| 区域 | 原版 | 重构版 | 差 |
|---|---|---|---|
| East | 1490.25 | 2679.25 | +1189.00 |
| South | 440.35 | 300.35 | −140.00 |

- East：第 4 行 `"1,234.50"` 解析失败，沿用了第 3 行的 `45.50`；重构版把千分位逗号去掉后正确算出 `1234.50`。差 = `1234.50 − 45.50 = 1189.00`
- South：第 8 行金额为空，沿用了上一行的 `140.00`；重构版跳过该行。差 = `140.00`

**注意 East 这个 bug 的阴险之处**：总额看起还是"有数"的，不是 0、也不是明显异常值，
只有跟源数据对账才会发现。

### bug 2：手写冒泡排序只跑了一趟

```python
for j in range(len(items) - 1):        # 一趟就结束了
    if items[j][1] < items[j + 1][1]:
        items[j], items[j + 1] = items[j + 1], items[j]
```

一趟冒泡只能保证**最大的那个冒到第一位**，其余位置全凭运气。4 个区域的实际输出：

```
原版：East 1490.25 / North 1599.5 / West 700.29 / South 440.35
                              ↑ 1599.5 > 1490.25，顺序错了
```

`North` 比 `East` 大，却排在后面。**2 个区域时它是对的**（这就是 `sales_clean.csv` 只有两个区域的原因）——
所以拿小样本测永远发现不了它。

### bug 3：同一张订单出现两次，算两遍

`DO-2010` 在脏数据里出现两行，原版直接加两次。North 因此多算了 `9.75`（`1599.5` vs `1589.75`）。

重构版保留第一条、忽略后面那条，并且**必须打印警告**：

```
WARN: duplicate order_id 'DO-2010'; later copy ignored
```

### 三个 bug 合起来

`TOTAL` 4230.39 → 5269.64，差 `1039.25`，正好等于 `1189.00 − 9.75 − 140.00`。
这个等式能对上，说明三处差异没有互相掩盖，每一处都独立可解释。

## 四、故意**不**改的地方

**输出格式**：新版仍然输出 `2645.5`，不是 `2645.50`。

看着别扭，但重构的定义是「对外行为不变」。`2645.5` 还是 `2645.50` 是另一个需求
（报表给财务看要不要补零），应该单独提、单独改、单独测。
**把它混在重构里，是最常见的事故来源**——出问题时你分不清是重构改坏的还是格式改坏的。

`report.py` 里那个 `format_amount()` 就是专门用来复现这个别扭格式的，代码注释写清了原因。

## 五、AI 建议里被否掉的两条

重构时把原版贴给 AI，它给了不少建议。**两条是必须拒绝的**：

**① "直接用 pandas 一行搞定：`pd.read_csv().groupby('region').sum()`"**

技术上对，但这是**替换**不是**重构**。替换会引入新依赖、新的数值精度语义（pandas 的 float64）、
新的空值规则（`sum()` 跳过 NaN 还是当 0），每一条都可能让总额变化——而你的安全网是"输出不变"。

判断标准很简单：**它会不会让 `check_equivalence.py` 变红？** 会，就不是重构。

**② "给 `parse_amount` 加个 `try/except` 返回 0，这样不会中断"**

这就是原版 bug 1 的翻版：错误被变成 0，数据静默丢失。
**返回 0 和 `pass` 是一回事**，只是换了个写法。正确做法是把错误**往上抛，由调用方决定跳过还是中止**，
并且跳过时必须留下警告。

> 这两条都不是"AI 很蠢"，而是 AI 看不到你的安全网。
> 你在 prompt 里写清"输出必须逐字节不变"，它才会给不破坏行为的建议。

## 六、这个练习的验收标准

1. **不看代码**，说清 bug 1 为什么会让 East 多出 1189.00
2. 说清为什么 `sales_clean.csv` 只有两个区域（提示：bug 2）
3. 把 `report.py` 的 `sorted(...)` 改成升序，`check_equivalence.py` 会在哪一步报红？为什么是那一步？
4. 如果给 `Order` 加一个 `quantity` 字段，哪些文件要改？（能答出"只有 models + loader"，说明分层理解了）

第 3 题的答案在 `check_equivalence.py` 的 A 段：**干净数据先红**，因为排序变了、输出就变了。
干净数据都过不了的改动，根本没资格进到 B 段——这就是"安全网优先"的意义。
